---
title: Início rápido
description: Obtenha o MillionSend e envie seu primeiro e-mail em poucos minutos.
---

O MillionSend funciona igual no [MillionSend Cloud](https://millionsend.com)
e na sua própria infraestrutura — mesmo painel, mesma API, mesmos SDKs.
Escolha sua implantação abaixo; as abas lembram sua escolha em toda a
documentação.

## 1. Obtenha o MillionSend

<DeploymentTabs>
<DeploymentTab deployment="cloud">

Cadastre-se em [millionsend.com](https://millionsend.com). Só isso — sem
infraestrutura, sem conta AWS. O painel fica em
[millionsend.com](https://millionsend.com) e a API em
`api.millionsend.com`.

</DeploymentTab>
<DeploymentTab deployment="self-hosted">

Você precisa de Docker (com Compose), Node 18+ e uma conta AWS com acesso ao
SES. Contas AWS novas começam no sandbox do SES, que só envia para
destinatários verificados —
[solicite acesso de produção](https://docs.aws.amazon.com/ses/latest/dg/request-production-access.html)
para enviar a qualquer um.

Um comando, em um diretório vazio — sem clonar nada:

```sh
mkdir millionsend && cd millionsend
npx @millionsend/setup
```

O assistente detecta o que já existe no diretório e oferece cada etapa: criar
o `.env` com segredos gerados, provisionar os recursos da AWS (usuário IAM +
política, tópico SNS de eventos, fila SQS de eventos, configuration set do SES —
mais uma assinatura de push quando sua implantação tem URL HTTPS pública), depois baixar o
arquivo compose e subir a imagem pré-construída com `docker compose up -d`.
Toda etapa pode ser pulada e é segura de repetir; `--dry-run` imprime o plano
completo sem tocar em nada.

Ao terminar: painel em `http://localhost:3000`, API em
`http://localhost:3001`. O primeiro usuário a se registrar vira a conta
inicial — depois disso o cadastro fica fechado, a menos que você opte por
abri-lo. Prefere fazer manualmente, ou está indo para produção? Veja
[Auto-hospedagem](/pt-BR/self-hosting).

</DeploymentTab>
</DeploymentTabs>

## 2. Verifique um domínio de envio

O MillionSend só envia a partir de domínios que você verificou.

1. No painel, vá em **Domínios** e adicione um domínio que você controla
   (ex.: `acme.dev`).
2. Adicione os registros DNS exibidos — um registro TXT de DKIM e os
   registros de MAIL FROM — no seu provedor de DNS.
3. Clique em **Checar DNS**. O MillionSend também resolve os
   registros ao vivo, então você vê na hora quais ainda faltam.

## 3. Crie uma chave de API

Vá em **Chaves de API** e crie uma. O token `ms_` é exibido uma única vez —
copie agora. Chaves podem ter acesso total ou somente envio, e opcionalmente
ficar restritas a um único domínio.

## 4. Envie um e-mail

Sua URL base da API:

<DeploymentTabs>
<DeploymentTab deployment="cloud">

`https://api.millionsend.com`

</DeploymentTab>
<DeploymentTab deployment="self-hosted">

A origem da API da sua instância — `http://localhost:3001` em um compose
local, ou o hostname em que seu reverse proxy serve a API (`PUBLIC_API_URL`,
ex.: `https://api.acme.dev`). Os
exemplos abaixo usam a URL da Nuvem; troque pela sua.

</DeploymentTab>
</DeploymentTabs>

Com curl:

```sh
curl -X POST https://api.millionsend.com/emails \
  -H "Authorization: Bearer ms_..." \
  -H "Content-Type: application/json" \
  -d '{
    "from": "Acme <onboarding@acme.dev>",
    "to": ["success@simulator.amazonses.com"],
    "subject": "Hello from MillionSend",
    "html": "<strong>It works!</strong>"
  }'
```

Ou com o SDK de Node (`npm install millionsend`):

```ts
import { MillionSend } from "millionsend";

const ms = new MillionSend("ms_...", { baseUrl: "https://api.millionsend.com" });

const { data, error } = await ms.emails.send({
  from: "Acme <onboarding@acme.dev>",
  to: "success@simulator.amazonses.com",
  subject: "Hello from MillionSend",
  html: "<strong>It works!</strong>",
});

if (error) console.error(error.name, error.message);
else console.log("sent", data.id);
```

Ambos retornam `{ "id": "..." }`. Acompanhe o e-mail indo de `queued` a
`delivered` na página **E-mails**.

<Callout type="info">
Em uma instância auto-hospedada, eventos de entrega (entregue, bounce,
reclamação) exigem o pipeline de eventos do SES que o assistente de setup
configura — veja
[Auto-hospedagem → Eventos do SES](/pt-BR/self-hosting#eventos-do-ses-bounces-reclamações-e-entregas).
Na Nuvem eles fluem automaticamente.
</Callout>

Já usa o Resend? Aponte o SDK oficial do Resend para o MillionSend — defina
`RESEND_BASE_URL` com a sua URL base e use sua chave `ms_`. O formato da
API é idêntico.

## Testes

- Para testar de ponta a ponta sem mandar e-mail para ninguém, envie para
  `success@simulator.amazonses.com`, como nos exemplos acima: o SES simula a
  entrega, e o e-mail aparece como `delivered`, com os webhooks `email.sent` e
  `email.delivered` (sem aberturas nem cliques: ninguém lê o e-mail). Endereços
  com `+` também funcionam: `success+cadastro@simulator.amazonses.com`.
- O SES não conta os e-mails do simulador na própria cota de envio nem nas
  taxas de bounce e reclamação, mas na Nuvem cada envio ainda conta na cota do
  seu plano, como qualquer outro e-mail. Em uma instância auto-hospedada, o
  simulador funciona mesmo com a sua conta AWS ainda no sandbox do SES, e a AWS
  cobra cada mensagem normalmente.
- Os endereços `bounce@`, `complaint@` e `suppressionlist@` do simulador geram
  bounces e reclamações que colocam o endereço na
  [lista de supressão](/pt-BR/concepts/suppressions) da sua equipe e disparam
  seus webhooks como os de verdade, mas nunca pesam na sua taxa de bounce ou de
  reclamação nem pausam seus envios. Cada endereço fica suprimido depois do
  primeiro uso; para repetir o teste, use um `+`:
  `bounce+2@simulator.amazonses.com`.
- Endereços em `example.com`, ou terminados em `.test` ou `.invalid`, não
  recebem e-mail, então um envio para um deles é recusado com `422` (veja
  [Erros](/pt-BR/api-reference#erros)).
